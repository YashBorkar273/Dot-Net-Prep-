## Part 1: Claude's summary (reference)

### 1. Value vs reference types: what gets copied
- **Value type** (`int`, `DateTime`, any `struct`): the variable holds the data itself. Assignment copies **all the fields**, so the two variables are independent.
- **Reference type** (`class`, `record`, `string`, arrays, `object`): the variable holds a **reference** (an address). Assignment copies the reference, so both variables point to **the same object**.
- **A struct copy is shallow.** If a struct holds a reference-type field, such as a `List<int>`, the copy duplicates the reference, and both structs share the list.

### 2. Where values live: the container rule
"Value types live on the stack" is **wrong as a rule**. A value type is stored **inline in its container**:

| Where the value is declared | Where it lives |
|---|---|
| Local variable in a normal method | Stack |
| Field of a class or record | Heap, inside that object |
| Element of an array (`Point[]`) | Heap, inside the array object; the array is a reference type |
| Local captured by a lambda, or used after an `await` | Heap, moved into a compiler-generated class |

- `new Point[3]` with `struct Point` creates **1 heap object** with 3 values inline.
- With `class Point`, it creates 1 array object holding 3 `null` references, plus 1 more object for each `new Point()`.

**Strong interview answer:** "Value types are stored inline in their container. A local goes on the stack, and a field of a class goes on the heap inside the object. The difference that matters is copy semantics, not location."

### 3. Boxing and unboxing
- **Boxing:** converting a value type to `object` or an interface **allocates a new heap object and copies the value into it**. The original and the box are then independent.
- **Unboxing:** `(int)obj` type-checks and **copies the value back out**.
- **Hidden sources:** `ArrayList` and other non-generic collections, methods that take `object` parameters, and calling an interface method on a struct through the interface.
- **The cost in a loop:** every iteration allocates. Short-lived boxes mean more frequent **gen 0 collections**, which take CPU time and pause threads. Boxes that are kept alive (stored in an `ArrayList`) add **memory overhead**: roughly 24 bytes per box plus an 8-byte reference, versus 4 bytes inline in `List<int>`. They also get promoted to gen 2.
- **The fix:** generics (`List<int>`) store values inline, so nothing is boxed.
- ⚠️ **Your misconception:** "boxing fills the heap." The heap doesn't fill up; the GC keeps collecting. The problem is **GC pressure**, meaning the GC has to run more often.

### 4. struct vs class vs record: equality

| | Kind | `==` by default | Assignment copies |
|---|---|---|---|
| `class` | reference | same object? | the reference |
| `struct` | value | not defined unless you add it (`Equals` compares fields) | the whole value |
| `record` / `record class` | **reference** | compares values (generated) | the reference |
| `record struct` | value | compares values (generated) | the whole value |

- `ReferenceEquals(a, b)` checks **identity** (the same object), whatever equality the type defines. Two separate `new` calls always give `false`.
- `with` creates a **new** record and leaves the original unchanged.

### 5. Strings
- `string` is a **reference type** that behaves like a value: it's **immutable**, and `==` compares content.
- `b = a` copies the **reference**; both variables point to the same string. `b += "x"` **creates a new string** and points `b` at it, so `a` is unchanged.
- `+=` in a loop copies everything built so far on every pass: quadratic time, and lots of garbage. Use `StringBuilder`, then call `ToString()` once.

### 6. Garbage collector
- It starts from **roots** (locals, statics, registers), marks every reachable object, frees the rest, and compacts the survivors.
- **When it runs:** mostly when gen 0's allocation budget fills up, and also under low system memory or on `GC.Collect()`. Don't call `GC.Collect()` in production code. It doesn't run on a timer.
- **Generations exist because most objects die young.**
  - **Gen 0** holds new objects and is collected often and cheaply.
  - **Gen 1** is a buffer.
  - **Gen 2** holds long-lived objects and is collected rarely and expensively.
  - Survivors are **promoted** a generation. They then leave gen 0, so gen 0 collections skip them and stay fast.
- **LOH (Large Object Heap):** objects of **85,000 bytes or more**. They count as gen 2 from the moment they're allocated, are collected only with gen 2, and aren't compacted by default, so the LOH can fragment.
  - The bigger cost: heavy LOH allocation **triggers frequent full gen 2 collections**.
  - The fix: `ArrayPool<byte>.Shared`, or streaming instead of buffering.

### 7. IDisposable: the GC frees memory, Dispose frees resources
- The GC knows nothing about **OS resources** (file handles, sockets, database connections) and runs at times **you don't control**.
- `Dispose()` gives **deterministic** cleanup: the resource is released now.
- `using` / `using var` guarantees `Dispose()` runs, even when an exception is thrown.
- **If you forget to dispose:** the problem isn't memory. You get locked files ("file in use by another process"), handle exhaustion, and with database connections, a **drained connection pool** and timeouts.
- **Finalizers** are only a safety net for classes that directly own unmanaged handles. They cost an extra GC cycle.
- **In ASP.NET Core**, the DI container disposes the services it creates. Don't dispose an injected `DbContext` yourself.
- **Writing a disposable class:**
  - Make it `sealed`, or use the full `Dispose(bool)` pattern.
  - Keep a `_disposed` flag and set it **before** releasing resources.
  - Make `Dispose()` safe to call twice.
  - Throw with `ObjectDisposedException.ThrowIf(_disposed, this)` when the object is used after disposal.
  - A *connection string* is just a `string`. The resource is the **connection** itself.

### Your weak spots from this session
- "Structs live on the stack." Use the container rule instead.
- "The heap fills up." It doesn't: the GC applies pressure, and resources leak.
- Explaining a consequence without the **mechanism**. Interviewers score the why.
